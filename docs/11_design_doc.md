# デザインドック

## テーマ

COMIUの中核設計: LINE中心のマルチテナント型イベント管理SaaS

## 課題

主催者はイベント運用で以下の課題を抱える。

- 予約受付がLINE DMやフォームに分散する
- 参加者情報の管理が手作業になる
- リマインドやキャンセル待ち対応が漏れやすい
- イベント終了後のレビュー/実績が資産化されない
- 新規参加者を検索から獲得しづらい

## 提案

- 主催者にはWeb管理画面を提供する
- 参加者にはLINE LIFF体験を提供する
- 公開SEOページにより検索流入を作る
- テナント単位でLINE/Stripe設定を持たせる
- スーパー管理者機能でSaaS運営を支える

## 設計原則

1. テナント分離を最優先する
2. 参加者体験はLINE内で完結させる
3. 公開ページは検索エンジンに理解されるHTMLを返す
4. 外部サービスの失敗を局所化する
5. 機密値をクライアントへ出さない
6. 設計判断をADRに残す

## 代替案

### 参加者も通常Webログインにする

却下理由:

- 対象ユーザーはLINE上での参加導線が自然
- サークル運用ではLINE通知が強い
- 登録摩擦が増える

### シングルテナントで始める

却下理由:

- SaaSとして複数団体を扱う前提
- 後からマルチテナント化するとDB/APIの影響が大きい

### 全ページをCSRにする

却下理由:

- SEOページが検索エンジンに弱くなる
- OGP/JSON-LDの品質が落ちる

## 主要設計

### 実装ステータス

このデザインドックのうち、イベント管理、予約、公開ページ、管理画面、LIFF基本導線は実装済みまたは一部実装済みである。一方、SEOの本格運用、セキュリティ強化、UGCの安全な公開運用は戦略フェーズであり、詳細は [SEO・セキュリティ・UGC戦略](12_seo_security_ugc_strategy.md) を正とする。

### マルチテナント

- `Tenant` を中心に各業務データを関連付ける
- 管理APIはJWT由来の `tenantId` を信頼する
- 公開URLは `tenant.code` を使う

### 予約

- 定員内は `reserved`
- 定員超過は `waitlisted`
- 決済必要時は `waiting_payment`
- チェックイン後は `attended`
- キャンセル時は `cancelled`

### SEO

- トップ、イベント、団体、カテゴリ、活用事例、料金をindex対象
- 管理/LIFF/認証系はnoindex
- Event/Organization/FAQPage/Breadcrumb/ItemList JSON-LDを使う

### 課金

- COMIU SaaS課金は運営側Stripe
- イベント決済はテナント別Stripe設定
- Webhookでプランや決済状態を同期する

## リスク

- LIFF APIでlineUserIdをクライアントから受ける箇所のなりすまし対策
- テナント秘密値の暗号化保存
- 大量イベント/メンバー時のページング不足
- Webhook失敗時のリトライ/再処理設計
- 監査ログ不足
